How the tracker is put together

Staff sign families up, give away books and run surveys from one web app. That app lives on Vercel, everything behind it lives in one Neon project, and the code lives on GitHub. This page shows how those pieces connect and what happens when one of them has a bad day.

The system at a glance

Numbers follow one staff visit, in order. They match the steps below. On a phone, scroll the map sideways.

One visit, step by step

  1. Open the appThe browser loads the staff web app from Vercel.
  2. Sign inStaff sign in with email or Google. The request goes through the relay on Vercel to Neon Auth, which confirms the email address with a code.
  3. Ask the APIEvery search, intake or giveaway goes from the browser straight to the Tracker API on Neon, carrying the sign-in token.
  4. Check who's askingThe API confirms the token with Neon Auth, then checks the email is verified and on the staff list.
  5. Read and saveThe API reads or writes families, books, stock and survey answers in Postgres. Two staff giving the last copy at once can't push stock below zero.
  6. Look up a new bookThe first time an ISBN is scanned, the API fetches its title, author and cover from Google Books, then Open Library.
  7. Classify it onceAI models, reached through the Neon AI Gateway, tag the book's genre, reading level and language. The answer is saved with its source, so each ISBN is only classified once.

Who can get in, and where data goes

  • Anyone can create a sign-in account, but the API only answers verified emails that an admin has added to the staff list.
  • Admins add other staff, locations and surveys. Only admins can download the Excel workbook for building reports.
  • Family details (names, contacts, children, ZIP, survey answers) are stored only in the Neon database.
  • Only book details, such as the ISBN, title and authors, go to the book catalogs and the AI models. Family information is never sent to them.
  • Testing happens on a separate dev copy of the database filled with made-up families. The demo script refuses to run on production.
Release process today

One person runs the deploy commands from a laptop. That keeps things simple, but a merged fix stays unreleased until someone deploys it. Automatic deploys from GitHub would be an easy next step.

What each piece does, and what happens if it's down

Most pieces have a fallback. The two that don't are sign-in and the database.
